## 1. Введение и суть техники

**DLL Sideloading** ([T1574.001](https://attack.mitre.org/techniques/T1574/001/)) — это архитектурная особенность и техника выполнения кода, при которой механизм загрузки библиотек операционной системы Windows перенаправляется на загрузку сторонней библиотеки `.dll` из каталога приложения вместо оригинальной или системной библиотеки.

---

## 2. Механизм работы

- **Стандартный порядок поиска DLL (DLL Search Order)**: По умолчанию при неполном указании пути Windows начинает поиск запрашиваемой библиотеки с директории, в которой расположен исполняемый файл (`.exe`).
- **Неявный вызов `LoadLibrary`**: При использовании импорта по имени без указания полного пути программа доверяет содержимому своей локальной папки.

Операционная система Windows выполняет поиск библиотеки по строго определенному алгоритму:

1. **Current Working Directory (CWD)** (Текущий рабочий каталог) — Каталог, из которого запущено приложение.
2. **System Directory** (Системный каталог) — Обычно `C:\Windows\System32`.
3. **16-bit System Directory** (16-битный системный каталог) — Обычно `C:\Windows\System`.
4. **Windows Directory** (Каталог Windows) — Обычно `C:\Windows`.
5. **Application Directory** (Каталог приложения) — Каталог, содержащий исполняемый файл (`.exe`).
6. **Directories in the PATH Environment Variable** (Каталоги из переменной окружения PATH) — Любые каталоги, перечисленные в системной переменной `PATH`.
7. **Application Data Directory** (Каталог данных приложений / AppData) — Расположения для хранения специфических данных приложений.

Чтобы приложение не завершалось аварийно из-за отсутствия необходимых экспортируемых функций (ошибка _«Точка входа не найдена»_), используется архитектурный паттерн **DLL Proxying**:

1. Сторонняя библиотека экспортирует те же имена функций, что и оригинальная DLL.
2. При вызове функции сторонний модуль выполняет необходимую внутреннюю логику.
3. Все остальные стандартные вызовы прозрачно перенаправляются (экспортируются) в настоящую системную библиотеку из каталога `System32` с помощью прагм компоновщика:

##### Создание прокси-DLL и payload

Создадим наш безвредный `payload`, который вызывает `calc.exe`, в бинарном виде:
```
msfvenom -p windows/x64/exec CMD=calc.exe -f raw -b "\x00" -o shellcode.update
```

Далее нужно создать *proxy DLL*, копируем исходную *DLL* (из `C:\Windows\System32\`) в отдельную директорию и воспользуемся инструментом [SharpDllProxy](https://github.com/Flangvik/SharpDllProxy). 
После клонирования репозитория соберите его в Visual Studio.

Также передаем наш `payload` в директорию с *DLL*

После передачи файла можно использовать `SharpDLLProxy.exe` для сборки прокси-DLL:

В результате получаем 2 файла:

Теперь перемещаем файлы на целевую виртуальную машину. Мы знаем, что программа ищет *DLL* по пути `C:\Program Files\Notepad++\updater`, поэтому помещаем туда три файла:
